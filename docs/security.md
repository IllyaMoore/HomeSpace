# Security

## Trust model

HomeSpace is **single-operator software**. Anyone holding the bearer token can
read every configured root and start a Claude Code process on the NAS with
whatever permissions the agent's mode grants. There are no user accounts and no
per-root permissions.

Treat the token as equivalent to a shell account on the box, and run the daemon
as a user that owns only what you are willing to expose. Do not run it as root.

## Authentication

A single bearer token, generated by `homespace init` as 32 random bytes
(base64url), stored in a `0600` config file.

- Presented as `Authorization: Bearer <token>`, or as `?token=` where a header
  is impossible — `EventSource` cannot set headers, and neither can an `<img>`
  or `<video>` tag pointing at a raw file.
- Compared with `timingSafeEqual` over fixed-width buffers. Comparing raw
  buffers throws on a length mismatch, which is itself a length oracle, so both
  sides are padded to 64 bytes first and the length is checked separately.
- `/api/health` is the one unauthenticated route. It returns the service name,
  version and time — enough for a client to confirm it found a HomeSpace daemon
  before it has a token, and nothing about the filesystem.
- An empty token in the config is fatal at startup rather than open-by-default.

Rotate with `homespace token --rotate`, restart the daemon, and re-pair each
client.

## The root sandbox

This is the part that matters most, and it is enforced in one place —
`src/core/paths.ts` — that every file handler and every agent workspace goes
through.

`resolveWithinRoot()` runs two independent checks:

1. **Lexical.** `resolve()` collapses `..` segments, then `relative()` confirms
   the result still sits under the root. This catches `../../etc/passwd` and
   traversal buried mid-path such as `docs/../../../etc`.

2. **Physical.** `realpath()` follows symlinks and the result is re-checked
   against the root's own realpath. A NAS share is full of symlinks, and one
   inside an allowed root can point at `/etc`. The lexical check alone would
   pass it.

The second check has a wrinkle: `realpath()` throws on a path that does not
exist yet, which is the normal case when something is about to be created. So
the code walks up to the deepest ancestor that *does* exist, resolves that, and
re-attaches the tail — meaning a symlinked **ancestor** is caught even when the
leaf is absent.

Also rejected: null bytes in a path, and unknown root ids (404, so the set of
configured roots is not enumerable by probing).

Symlinks that leave a root are still *listed* — they exist on disk, and hiding
them would be dishonest — but opening one returns 403.

Verified by `tests/paths.test.mjs` and again over HTTP in
`tests/server.test.mjs`, including raw-socket requests that bypass a client's
URL normalisation.

The static file server applies the same containment check against `web/`, so
`GET /../../../../etc/passwd` on a raw socket serves the app shell, never the
file.

## Agent permissions

Each agent carries a Claude Code permission mode. From safest:

| Mode | Effect |
| --- | --- |
| `plan` | Read-only. Produces a plan and changes nothing. |
| `manual` | Asks before every tool use. |
| `acceptEdits` | Auto-approves file edits; other tools still ask. |
| `auto` | Claude decides when to ask. |
| `dontAsk` | No prompts. |
| `bypassPermissions` | Every permission check skipped. |

Two guards apply:

- An agent can only be created on a root marked `workspace: true`. A media
  share stays browsable and unwritable.
- `bypassPermissions` is refused on a root marked `readOnly`, because the
  combination is a contradiction the operator did not mean.

**`manual` has a gap today.** The daemon does not yet surface a permission
prompt in the UI, so a session in `manual` mode can stall waiting for an answer
nobody can give. Use `plan` for anything read-only and `acceptEdits` for work
inside a workspace you have backed up. An approvals queue is the next thing to
build.

### Auto-approved is not the same as allowed

The agent form has two tool fields, and they do different things:

- **Auto-approved tools** maps to `--allowed-tools`. These run without a
  permission prompt. It is *not* a restriction — the agent can still use tools
  that are not on the list.
- **Denied tools** maps to `--disallowed-tools`. This is the field that
  actually stops the agent doing something.

If you want to constrain an agent, use the denied list, or `plan` mode.

## Network

- Binds `127.0.0.1` by default. Reaching it from the LAN is an explicit change.
- No TLS. Put it behind a reverse proxy with a certificate if it leaves the
  LAN — the token crosses the wire on every request.
- Cross-origin requests are refused unless the origin is in
  `server.allowedOrigins`. Same-origin — the normal case, since the daemon
  serves the UI — always passes.
- `x-content-type-options: nosniff`, `x-frame-options: SAMEORIGIN` and
  `referrer-policy: no-referrer` on every response.
- Request bodies are capped at 1 MiB.

## Resource limits

Bounded so a runaway client cannot exhaust the NAS: concurrent sessions,
per-session idle timeout, transcript length, text preview size, and the search
walk (directories visited, depth, hits). Each reports when it bites — a
truncated search says `truncated: true` rather than pretending it finished.

## Data at rest

- `config.json` is `0600`, its directory `0700`. It holds the token in plain
  text; file permissions are the only thing protecting it.
- `agents.json` is `0600` under `dataDir`. It holds agent instructions, which
  may be sensitive.
- Transcripts live in memory only. They are lost on restart — which also means
  they are never written to a NAS share by accident.
- Claude Code keeps its own session history under the daemon user's home
  directory, on its own terms.

## Not covered

- Multiple users, roles, or per-root access control.
- TLS termination.
- Audit logging of who did what.
- Rate limiting or brute-force lockout on the token. A 32-byte random token is
  not guessable, but a determined attacker on the LAN can try as often as they
  like.
- Sandboxing the agent itself. Once a Claude Code process is running, its reach
  is whatever its permission mode and the daemon user's account allow.
